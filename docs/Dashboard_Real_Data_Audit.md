# Dashboard Real Data Audit & Implementation Plan

## 1. Audit Findings

**A. Values already from real API:**
- `deviceConnected`, `deviceStatus`, `batteryStatus`, `lastSync`
- `todayExposure`, `todayDose`
- `peakUv`, `averageUv`, `currentUv`
- `currentRisk`, `currentSpfRecommendation`
- `activeProtection`, `protectionRemaining`

**B. Values still mock/static:**
- **Hourly UV Chart**: 24-slot timeline generated by `useUVData.ts` (pseudorandom sinusoids).
- **Peak UV Time**: Generated by `useUVData.ts`.
- **Lowest UV Value**: Generated by `useUVData.ts`.
- **Burn Time Remaining**: Hardcoded to `"24 min"` in `Dashboard.tsx`.

**C. Backend data that exists but is not exposed:**
- **Peak UV Time**: The backend already iterates through today's readings to find `peakUv`, but discards the timestamp.
- **Lowest UV Value**: The backend has all of today's readings, but doesn't calculate the minimum.
- **Burn Time Remaining**: `CalculationService` already implements `calculateUnprotectedBurnTime(uvIndex, skinType)` and `calculateProtectedBurnTime(unprotectedBurnTime, spf)`, but these are not currently invoked by the `DashboardService`.
- **Hourly Chart Data**: The backend pulls all of today's `uVReading` records. These just need to be grouped by the user's local hour.

**D. Values requiring new calculations/queries:**
- **Hourly Chart**: Needs a time-bucket aggregation algorithm inside `DashboardService` to map raw UTC readings into 24 local-time hour slots using a `tzOffset` query parameter.
- **Lowest UV**: Needs to ignore missing data (no fabrication of `0`) and identify the true minimum recorded reading from the device.
- **Burn Time**: Needs to be computed by invoking existing `CalculationService` methods based on `currentUv`, `skinType`, and `activeProtection`.

**E. Values to remain for later phase:**
- None. The backend currently possesses all required data, dependencies, and formulas to compute these remaining metrics in real-time.

## 2. Recommended Implementation

### Step 2: Hourly UV Chart
- **Frontend**: Pass `tzOffset = new Date().getTimezoneOffset()` in the `/api/v1/dashboard` polling request.
- **Backend**: Update `DashboardService` to initialize a 24-element array of zeros. Iterate through `todayReadings`, adjust the UTC timestamp to local time using `tzOffset`, and assign the maximum UV value for that hour to the corresponding slot. Mark the local current hour with `isCurrent: true`.

### Step 3: Peak UV Time
- **Backend**: While computing `peakUv` in `DashboardService`, simultaneously store the `recordedAt` timestamp as `peakTime`. Return it as an ISO string.
- **Frontend**: Use `new Date(data.peakTime).toLocaleTimeString(...)` to display the formatted time.

### Step 4: Lowest UV Value
- **Backend**: Initialize `lowUv = null` and `lowTime = null`. Iterate through `todayReadings` (which represents actual data points, no fabricated zeroes). Find the minimum reading. Return both values.
- **Frontend**: Update the Dashboard to handle a `null` low UV value appropriately (e.g., displaying "N/A" or hiding it if no data exists).

### Step 5: Burn Time Remaining
- **Backend**: In `DashboardService`, pass `currentUv` and `skinType` to `calcService.calculateUnprotectedBurnTime`. If `activeProtection` is true, pass the result to `calcService.calculateProtectedBurnTime` using the active sunscreen's SPF.
- **Frontend**: Replace the hardcoded `"24 min"` string with the calculated integer, or `"Safe"`/`"N/A"` if the backend returns `null` (UV is 0).

## 4. API Changes Required

**Request (`GET /api/v1/dashboard`)**
- Add optional query parameter: `?tzOffset=<number>`

**Response Payload Additions**
- `peakTime`: `string` (ISO date) | `null`
- `lowUv`: `number` | `null`
- `lowTime`: `string` (ISO date) | `null`
- `burnTimeRemaining`: `number` | `null`
- `hourlyData`: `Array<{ hour: string, uv: number, isCurrent: boolean }>`

*(Note: API backwards compatibility is maintained as new fields are strictly additive).*

---

## 5. Risks
- **Timezone Drift**: If the frontend `tzOffset` does not perfectly match the day boundary `startOfDay` used in the backend's `getTodayReadings` query, the hourly chart could clip readings near midnight. (Currently, `startOfDay` uses UTC midnight, which might omit local morning readings for users behind UTC, or include yesterday's local evening readings for users ahead of UTC). **Mitigation**: Adjust `getTodayReadings` to use a local-time adjusted `startOfDay` based on the provided `tzOffset`.
